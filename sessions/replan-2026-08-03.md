# App Replan: Dark Trading Desk, Trustworthy Live Screener, and Observable AI

**Status:** Draft for team review  
**Prepared:** 2026-08-03  
**Repository:** `Segev191312010/aiautomation`  
**Code baseline reviewed:** `9628a7eebf9f9dc839ca0790ff76c521ee9eb1dd` on `master`

## Purpose

This is an implementation-ready replan for turning the existing application into a coherent, operator-trustworthy trading desk before a PAPER soak and any progression toward LIVE operation. It is deliberately a focused evolution of the current architecture, not a backend rewrite or a redesign that discards tested behavior.

The plan was validated against the repository at the commit above. It corrects several assumptions in the earlier draft:

- The current backend suite is **739 passing tests**, not 502.
- The current dashboard suite is **31 passing test files / 389 passing tests**, not 259.
- The application already has a dark token set and an AI health contract; both need normalization and extension rather than replacement.
- The existing market-data WebSocket already supports symbol subscription and ref-counted unsubscribe. The screener should reuse it, not add another channel.
- The canonical fill notification emitted by the backend is `order_filled`, with payload fields nested in `data`. The frontend currently listens for `filled` and reads the wrong envelope, so the fix is a contract alignment, not duplicate event emission.
- Bull/bear debate failures already produce a degraded result and record debate parse failures. Multi-persona parse failures remain insufficiently observable.

### Architecture to retain

The following parts are solid enough to extend rather than replace:

- **Backend domain boundaries:** routers, service modules, Pydantic contracts, bot health, runtime state, and the test suite are established.
- **Zustand domain stores:** the existing store split is useful. The work is selector discipline and a small amount of state ownership cleanup, not a reducer or slice rewrite.
- **Dual WebSocket design:** `/ws` is for application events and `/ws/market-data` is for market subscriptions. The latter already has subscribe/unsubscribe and ref-count handling.
- **Screener scan pipeline:** the scanner, cache, request models, and result types are the right extension points for freshness metadata and a manual force-refresh path.
- **Autopilot safety model:** OFF/PAPER/LIVE controls, server-side capability checks, emergency stops, direct-intent controls, and LIVE confirmation must remain authoritative.
- **CSS variable to Tailwind token indirection:** the `theme.*` convention is the correct theming mechanism. The palette and consumers need convergence.

## Product Outcomes

### Operator outcomes

1. An operator can tell, at a glance, whether the application, market-data feed, screener data, and AI decision path are healthy.
2. A screener scan can remain current during an active session without requiring repetitive manual clicks or pretending daily bars are live prices.
3. A PAPER AI run is observable from trigger through decision outcome, including degraded parsing and blocked actions.
4. Fill events update the operator interface promptly using a defined, tested event contract.
5. The desktop interface is a consistent dark trading desk rather than a mix of warm legacy surfaces and newer shell styling.

### Engineering outcomes

1. Every newly introduced API or WebSocket field has a typed backend contract, typed frontend contract, and automated test coverage.
2. Quote updates do not cause broad page re-renders.
3. Auto-refresh cannot create overlapping scans, stale-response overwrites, hidden-tab churn, or silent failures.
4. A PAPER soak can verify the end-to-end flow using observable health signals and explicit pass/fail criteria.

## Decisions

| Decision | Chosen direction | Reason |
|---|---|---|
| Default visual mode | Dark | The primary use case is a desktop trading desk. Keep light mode as a supported secondary mode. |
| Type pairing | Inter for UI text, JetBrains Mono for prices, timestamps, symbols, and diagnostics | Clear hierarchy and legible numeric scanning. JetBrains Mono is already part of the project’s intended typography direction. |
| Action accent | Amber | Use it narrowly for primary actions, warnings, and attention states. Green and red remain reserved for trading semantics. |
| Screener refresh cadence | Default 60 seconds; operator-selectable 30 / 60 / 120 seconds | Avoid hidden adaptive behavior. The operator should know the load and cadence chosen. |
| Cache bypass | Manual only | A normal live refresh remains cache-backed. “Force refresh” is explicit and never runs on a timer. |
| Live screener pricing | Subscribe the top 20 currently visible rows through existing market-data WS | Provides meaningful live context while bounding subscription load. |
| Fill event | Standardize frontend on `order_filled` and normalize its `data` envelope | Preserve one canonical backend event instead of broadcasting aliases. |
| Decision stream | Initial history via REST, newest outcomes via `decision_run` WS event | Bounded, resilient feed with a recoverable source of truth. |
| Primitive library | Build only primitives with immediate consumers | Avoid a broad component-library rewrite before the first vertical slice proves the API. |
| Icons | Retain existing shared icons initially; introduce `lucide-react` only for new or duplicated UI work | Avoid unnecessary migration churn in the foundation PR. |

## Scope and Non-Goals

### Included

- Dark-theme normalization and a small token-driven primitive layer.
- Reliable screener refresh, freshness semantics, and top-result live quote enrichment.
- AI parse-failure telemetry, operator-visible AI status, and a live decision outcome feed.
- Correct fill-event handling.
- Autopilot and dashboard vertical-slice rebuilds that consume the new primitives and granular selectors.
- A revised paper-soak runbook and explicit live-readiness evidence.

### Explicitly excluded

- Rewriting the 182-endpoint backend surface.
- Adding a second LLM provider.
- Adding a third WebSocket channel for screener results.
- Per-tick rerunning of the screener universe.
- Replacing all Zustand stores or converting to a new state-management library.
- A mobile-first redesign. Existing responsive behavior must not regress, but desktop remains the design target.
- A broad “remove every hardcoded color in the repository” cleanup as a release gate. The audit currently finds over one thousand color references; migration will be controlled page by page.

## Known Gaps and Corrections

### Visual system

- The current application contains dark theme variables, but dark is not the reliable default and the token system coexists with legacy warm/cream styling.
- `index.css` defines large panel/card radii and a font stack that conflicts with Tailwind’s configured type direction.
- `tailwind.config.ts` contains both semantic `theme.*` mappings and a separate hardcoded `terminal.*` palette. New UI must use the semantic mappings.
- The color audit is substantially larger than the four shared components called out in the earlier draft. The correct strategy is to stop adding raw colors, tokenize primitives, and convert touched pages in sequence.
- `ui/` currently provides application chrome such as skeletons, toasts, offline/session states, and error boundaries. It does not yet provide reusable input, button, card, badge, tab, or stat primitives.

### Screener and market data

- The scan cache TTL is 900 seconds. The scan response currently has no top-level scan timestamp, row freshness metadata, or `force_refresh` request field.
- A daily OHLCV bar’s timestamp is not the same thing as cache freshness. The UI must distinguish the time of the underlying bar from the time the cache was last refreshed.
- The frontend screener is manual today. It has no visibility-aware refresh lifecycle, request sequencing, or next-refresh presentation.
- The dedicated market-data WebSocket can already subscribe by symbol. The screener should bind its top visible rows to this service and unsubscribe on result/page changes.
- Data health is owned in `backend/main.py` and stored through `backend/runtime_state.py`; adding a `screener` source requires wiring the scanner execution path to that monitor, not only editing `data_health.py`.

### AI and events

- `run_bull_bear_debate` already records a parse failure and returns a degraded result, but its payload does not expose a specific degradation reason.
- `run_multi_persona_analysis` falls back to an unavailable/zero-score result on JSON parse failure without comparable telemetry. This is the primary silent AI failure to fix.
- The existing `AIStatusResponse` already exposes capability, configured-provider state, safety state, optimizer state, and bot health. Extend this contract; do not create duplicate status names such as both `mode` and `autopilot_mode`.
- The existing `order_filled` backend event places the fill payload under `data`. The frontend hook subscribes to `filled` and reads top-level fields. Both the event name and payload normalization need correction.
- A decision ledger already exists. The new event should publish only finalized decision-run summary data and the UI should recover history through the existing REST surface.

### Performance and page structure

- Several pages and shared components subscribe to whole Zustand stores, including Autopilot, Analytics, Trade Bot, Market, Positions, Watchlist, and Header paths. These must be converted to narrow selectors as their pages are touched.
- `AutopilotPage.tsx` is already a large orchestration component with useful existing subcomponents. Split lifecycle/data orchestration from presentation; do not discard working panels for a ground-up rewrite.
- `Dashboard.tsx` is also a substantial page. Rebuild it as a bounded command-deck vertical slice, not as a single mega-component.

## Phase 2: Trustworthy Live Screener

### Goal

Give operators an honest, visible refresh lifecycle and live quote enrichment for a bounded subset of results. The screener remains a scan system, not a per-tick universe-ranking engine.

### Navigation scope

This phase also absorbs the Swing Screener into the unified Screener route. The page uses controlled views/tabs for the standard scanner and Swing research rather than maintaining two competing top-level operator destinations.

### API contract

Extend the screener request and response intentionally.

#### Request

Add to `backend/models.py::ScanRequest` and the matching dashboard request type:

```ts
force_refresh?: boolean // default false
```

`force_refresh` is accepted only for an explicit user action. Timed live refreshes send `false`.

#### Response

Add a top-level completion time and clear row-level freshness fields:

```ts
type ScanResponse = {
  scanned_at: string                 // ISO-8601 time when this scan completed
  results: ScanResultRow[]
  skipped: string[]
  elapsed_ms: number
  total_symbols: number
}

type ScanResultRow = {
  // existing fields
  bar_as_of?: string                 // timestamp of the latest source OHLCV bar
  cache_refreshed_at?: string        // when this symbol’s cached bars were fetched
  cache_age_seconds?: number
}
```

Do not use a single ambiguous `data_age_seconds` field. A one-day bar can be valid for a daily strategy while still being hours old, and a freshly fetched cache can still contain a prior-session bar. The UI labels both concepts separately:

- **Scan completed:** time the response was produced.
- **Bar as of:** time of the underlying OHLCV observation.
- **Cache age:** time since that data was fetched.
- **LIVE:** shown only when the row has an active market-data quote subscription.

### Backend implementation

| Work item | Primary files | Implementation detail |
|---|---|---|
| Request model | `backend/models.py`, `backend/routers/screener_routes.py` | Add and pass `force_refresh`; retain default behavior for existing clients. |
| Cache control | `backend/screener.py` | Implement targeted cache invalidation/reload for the requested symbols only when `force_refresh=true`. Do not disable the global cache. |
| Timestamping | `backend/screener.py` | Capture scan completion with timezone-aware UTC time. Attach source bar and cache timestamps only when known. |
| Health integration | `backend/main.py`, `backend/runtime_state.py`, `backend/screener.py` | Register a `screener` freshness source and report scan success/failure from the scan execution path. Preserve existing `watchlist_quotes` and `ws_quotes` monitoring. |
| Backend tests | `backend/tests/test_screener*.py`, health tests | Cover new defaults, metadata, forced refresh, scanner errors, and health recording. |

Force refresh must be guarded against accidental loops:

- It is invoked from the explicit Force refresh button only.
- The dashboard disables the button while a forced request is outstanding.
- It is never used by `useScreenerAutoRefresh`.
- If provider-level limits are encountered, the API returns a typed, user-displayable error rather than falling back silently.

### Frontend state and lifecycle

Keep durable screen state in `screenerStore`; keep browser timers and abort controllers in a hook rather than serializing them into Zustand.

#### Store additions

Add only renderable, serializable state:

```ts
auto_refresh_enabled: boolean
refresh_interval_seconds: 30 | 60 | 120
last_scan_at: string | null
next_refresh_at: string | null
scan_status: 'idle' | 'loading' | 'refreshing' | 'error'
scan_error: string | null
```

`runScan` accepts an options object including `forceRefresh`, `reason`, and a monotonic `requestId`. The reducer ignores a response whose request ID is older than the latest accepted request.

#### Refresh hook

Add `dashboard/src/hooks/useScreenerAutoRefresh.ts`:

1. Starts one interval only when Live mode is enabled and the document is visible.
2. Uses the selected 30/60/120-second interval, defaulting to 60 seconds.
3. Stops on `visibilitychange` when hidden.
4. Performs one catch-up scan when the tab becomes visible if the scheduled time elapsed.
5. Uses an `AbortController` for the active request and aborts it on unmount, scanner replacement, or a new explicit scan.
6. Never launches a second scan while one is in flight.
7. Exposes countdown state for the control bar.

### Live quote enrichment

Reuse `wsMdService` and the existing `/ws/market-data` backend route.

1. After a scan result set is rendered, derive the first 20 currently visible symbols after the operator’s active sort and filter.
2. A `useScreenerLiveQuotes(symbols)` hook subscribes those symbols through `wsMdService`.
3. On sort/filter/scan/page changes, calculate the set delta, unsubscribe removed symbols, and subscribe new symbols.
4. On page unmount, unsubscribe every screener-owned symbol.
5. Rows receive quote updates through a narrow selector keyed to their symbol. A quote tick must not replace or rerun the full scan result array.
6. Display `LIVE` only after a current quote is received. Show a stale state when the quote exceeds the market-data service threshold.

The top-20 cap is a named constant, documented in code, and covered by a test. It is intentionally not configurable in the first release.

### Screener user interface

Rebuild `ScreenerPage.tsx`, `ScanResultsTable.tsx`, and the filter controls on the Phase 1 primitives:

- Control bar: universe, preset, filters, Manual/Live toggle, 30/60/120 interval, Scan now, Force refresh.
- Status line: `Last scan`, `Next refresh`, scan duration, result count, and human-readable scan failure.
- Table: sortable headers, semantic setup badges, cache/bar freshness presentation, and live quote indicator.
- Loading: use `SkeletonTable` during initial scan and a non-destructive refresh state during timed updates.
- Empty/error: show a tokenized empty state with a clear recovery action.
- Sparkline: defer until a compact trend data source is confirmed. Do not fabricate a visual from a single current quote.

### Screener acceptance criteria

- Given Live is enabled and the tab is visible, when 60 seconds elapse, then one cache-backed scan is started and the timestamp updates on success.
- Given the tab becomes hidden, when the next interval elapses, then no scan request is sent.
- Given an older request completes after a newer request, when its response arrives, then it cannot overwrite newer results.
- Given Force refresh is clicked, when the request is in flight, then a second force action is disabled and the request bypasses only targeted cache entries.
- Given a result is among the top 20 visible symbols and a quote is received, when a tick arrives, then that row updates its live price without rerunning the scan.
- Given a result has only daily bars, when the latest bar is from the previous session, then the UI identifies the bar time instead of claiming the price is live.

## Phase 3: AI Activation, Observability, and Event Contracts

### Goal

Make PAPER AI behavior understandable and auditable. An operator must distinguish a healthy decision, an intentionally shadowed decision, a blocked decision, a missing configuration, a provider error, and an unparseable response.

### AI failure telemetry

#### Multi-persona analysis

In `backend/ai_advisor.py::run_multi_persona_analysis`:

- Log structured warning fields on JSON parse failure: analysis type, model/provider, exception category, and a redacted response fingerprint or size. Never log raw prompts, API keys, or full provider content.
- Record a persona parse-failure counter using the same bounded/time-windowed approach as the existing debate failure tracking.
- Return a typed degraded result with `degraded: true` and `degradation_reason: "unparseable_persona_response"`.
- Preserve the current safe fallback score behavior while making the fallback visible.

#### Bull/bear debate

Keep the existing degraded result and debate counter. Extend the result payload with a specific machine-readable `degradation_reason`, such as:

```ts
'unparseable_bull_response' |
'unparseable_bear_response' |
'provider_failure' |
'timeout'
```

No raw model output should be returned to the browser.

#### Optimizer outcome classification

In `backend/ai_optimizer.py`, replace any generic “no API key or API failed” style outcome with a typed status:

```ts
type OptimizerOutcome =
  | 'applied'
  | 'shadowed'
  | 'blocked_by_guardrail'
  | 'skipped_no_provider_config'
  | 'skipped_provider_failure'
  | 'skipped_unparseable_response'
  | 'skipped_no_candidates'
  | 'cancelled'
```

Record the latest outcome, reason, timestamp, and safe aggregate counts. The browser receives summaries, never API credentials or decision prompts.

### Status contract

Extend the existing API status model rather than duplicating it.

Primary files:

- `backend/api_contracts.py::AIStatusResponse`
- the status builder that feeds `backend/autopilot_api.py`
- `backend/bot_health.py`
- dashboard API types and `autopilotStore`

Retain established fields such as `mode`, `autonomy_active`, `shadow_mode`, `ai_provider_configured`, `optimizer_running`, and `bot_health`. Add only missing operator signals:

```ts
last_optimizer_outcome?: OptimizerOutcome
last_optimizer_outcome_at?: string
last_optimizer_reason?: string
persona_parse_failures_24h: number
debate_parse_failures_24h: number
```

`ai_provider_configured` remains the safe boolean configuration signal. Do not add a redundant provider-key field.

### Fill event correction

Standardize on the backend’s existing canonical event:

```ts
{
  type: 'order_filled',
  data: {
    symbol: string,
    // order/fill details emitted by notification_service
    timestamp: string
  }
}
```

Implementation:

1. Add a typed frontend event normalizer that validates the outer `type` and reads fill fields from `event.data`.
2. Change the fill subscription in `dashboard/src/hooks/useWebSocket.ts` from `filled` to `order_filled`.
3. Update the handler to refresh or patch only the affected account/position/order data.
4. Keep `StatusPoller` as a recovery mechanism, not the primary path to visible fills.
5. Do not emit both `filled` and `order_filled`; aliases hide contract drift.

### Decision-run event

Publish a `decision_run` event only after a decision run has been finalized and stored.

```ts
{
  type: 'decision_run',
  data: {
    run_id: string,
    created_at: string,
    mode: 'OFF' | 'PAPER' | 'LIVE',
    outcome: OptimizerOutcome,
    source: string,
    applied_count: number,
    blocked_count: number,
    shadowed_count: number,
    confidence?: number,
    latency_ms?: number,
    degradation_reason?: string
  }
}
```

Implementation boundaries:

- The optimizer owns creating the decision summary, but not transport or WebSocket knowledge.
- Introduce a thin domain-event publisher interface in a dedicated `backend/events.py` module, unless repository review confirms that the existing `event_logger.py` is already an appropriate dependency-light event abstraction. Do not place this interface in `main.py`.
- `ai_optimizer.py` depends only on that publisher interface and emits a typed `decision_run` domain event after the ledger record is finalized.
- The FastAPI/WebSocket composition layer registers the publisher implementation at startup and adapts the domain event to the `/ws` broadcast envelope. This preserves a one-way dependency: optimizer → event interface ← application transport.
- Unit-test the optimizer with a fake publisher and test the WebSocket adapter separately. Neither test should require a running FastAPI server or a live WebSocket connection.
- The event contains no prompt, provider response, secret, or unbounded payload.
- The dashboard fetches its initial bounded history through the existing decision-ledger REST API, then prepends verified `decision_run` events.
- The feed is capped in the store and has a “view all” route or existing ledger drill-down for history.

### PAPER activation experience

Use the existing mode endpoint and server-side safety checks.

- When mode is OFF and provider capability is ready, show a primary `Start AI in PAPER mode` action.
- When capability is unconfigured or degraded, show the specific reason and a route to Settings rather than a dead control.
- When PAPER is active but shadow mode is enabled, explain that decisions are being evaluated but not applied.
- Preserve the existing typed LIVE confirmation and all server-side safeguards. The frontend cannot make LIVE “available” by itself.

### AI acceptance criteria

- Given a multi-persona model response cannot be parsed, when analysis completes, then a structured warning, counter increment, degraded response, and operator-visible health value are produced.
- Given an optimizer does not produce a decision, when the result is shown, then the UI identifies the typed skip/blocked reason rather than saying only “AI failed.”
- Given an order is filled, when the backend emits `order_filled`, then the frontend normalizes the `data` envelope and updates relevant UI without waiting for the poller.
- Given a decision run is finalized, when a connected dashboard receives `decision_run`, then the decision feed prepends one bounded, typed summary item.
- Given the WebSocket receives malformed data, when parsing fails, then the application continues safely and records a non-sensitive diagnostic rather than silently swallowing every failure.

### Soak criteria

Run at least one complete US equities PAPER session under normal operator monitoring. Record every check as PASS, FAIL, or NOT EXERCISED and include links or timestamps to supporting logs/ledger entries.

1. All required checks pass or have an approved documented exception.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Auto-refresh overloads yfinance/provider limits | Cache-backed timed scans, explicit 30/60/120 cadence, no timed force refresh, one request in flight. |
| Daily bars mislead operators as live data | Separate bar timestamp, cache age, scan completion, and true LIVE quote status. |
| Screener WS subscriptions leak | Top-20 cap, set-delta lifecycle, explicit cleanup, and ref-count tests. |
| AI fallback hides degraded behavior | Typed outcomes, degradation reason, counters, structured diagnostics, and visible status. |
| Event aliases drift again | One canonical event name, typed normalizer, backend and frontend contract tests. |
| Visual rewrite expands indefinitely | Primitive-first vertical slices; no global hardcoded-color eradication as a prerequisite. |
| Selector work introduces stale UI | Incremental replacement with focused tests around live quote and account updates. |
| LIVE is enabled prematurely | PAPER soak gate remains operationally separate; retain server-side safety controls. |
