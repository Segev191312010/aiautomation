**Can a 20 s settle pass while a child is crash-looping?**
- Not within the window. Any `CHILD_EXIT` of a required child after the new start, or a second `CHILD_START`, fails at once (:1876-1885).
- A dead pid without its exit line counts as missing, which leads to `post_start_timeout`, never to a pass.
- What it cannot see is a child whose *first* exit comes more than about 21 s after its `CHILD_START`. That is the same horizon as the manual L3-9 look.
- The settle has no deadline of its own, but it is bounded: it starts from a `CHILD_START` that has already happened.

**Does the mid-session acceptance weaken anything?** No.
- It is reachable only through `mid_session_ok=True`, which only `undo_to` passes (:2203, :2217).
- The undo still requires each of these:
  - `bridge       reviewed (sha256 <old pin>)`;
  - `database     schema v<applied> current`;
  - the fenced and heartbeat lines;
  - no `!!!` and no `WARNING:`;
  - exactly one `session      <D> (` line with exactly one `SESSION_START date=<D>` and no `SESSION_WAIT`;
  - one daily `SUPERVISOR_START` from the live entrypoint and no other supervisor;
  - telegram and heartbeat descending from it, with the 20 s settle;
  - the plist (`WorkingDirectory`, `ProgramArguments`, `is_current` unless `launchd.py` changed, `is_loaded`);
  - HEAD == PREV.
- `SESSION_OVER` (after the close) is refused by both checks (test :2913).
- With the MEDIUM-1 re-check, a deploy's steps are bounded (stop ≤ 75 s, dry run ≤ 300 s, start ≤ 80 s from ≤ 06:50 ET). So the mid-session form is a safety net for a jumped clock (sleep), not a path the tool normally takes.

## (3) New defects introduced by the fixes

### N17b-L1 (LOW, new): a SIGHUP/SIGTERM during a git write can SIGKILL git; the halt then judges "git never moved" from HEAD alone

**Where.**
- `signals_interrupt()` covers the whole of `_run` (:1597), including `fast_forward` → `GitWriter.merge_ff_only` (:623-626). It also covers `undo_to` → `reset_keep` (:628-631, :2172-2180), and all of `deploy undo` (:2390).
- `_halt_unexpected` (:2062-2081).

**Facts.**
- `DeploySignal` is a `KeyboardInterrupt`. When it is raised in the main thread while `GitWriter._run` waits in `subprocess.run`, CPython 3.11.15 `Popen.communicate` waits `_sigint_wait_secs = 0.25` s. Then `run`'s `except: process.kill()` sends SIGKILL to git (`~/.local/share/uv/python/cpython-3.11.15-macos-aarch64-none/lib/python3.11/subprocess.py:565-566, :882, :1214-1218`).
- A `merge --ff-only` or `reset --keep` killed mid-checkout can leave `.git/index.lock` and a partly updated working tree. The ref is updated last, so HEAD is still the old one.
- `_halt_unexpected` reads only HEAD. When HEAD == PREV it writes `next: git never moved (HEAD …): ( cd … && … shadow agent enable ), then the start lines` (:2073-2076).
- Before P2.1, a SIGTERM killed only the tool and git finished on its own. So the SIGKILL of git is new.
- SIGHUP from a closed window and Ctrl-C reach git directly through the foreground process group, as before. The new part there is the confident "git never moved" text.

**Failure scenario.** The probability is very small: a signal inside a write window of about 0.1-0.5 s, in a run of several minutes.
1. A SIGTERM lands during the ff.
2. git is SIGKILLed after writing some candidate files.
3. HEAD stays PREV. The deploys.log line says to enable.
4. The supervisor would start PREV with some candidate files in place. The bridge pin catches a changed bridge only. The leftover `index.lock` also blocks the printed 6.3 block's `git reset --keep`.

**Fix (small).**
- Around `GitWriter._run`, defer HALT_SIGNALS: record the signal and raise it after the write returns.
- Start git with `start_new_session=True`, so terminal-group SIGHUP/SIGINT do not reach it mid-write.
- In `_halt_unexpected`, say "git never moved" only when HEAD == PREV, `check_tree_clean` is benign and there is no `.git/index.lock`. Otherwise print the 6.3 block, adding `git -C <repo> status --short` (Expect: only benign).
- Test: a GitWriter whose `merge` gets `os.kill(os.getpid(), SIGTERM)` while it runs. Expect the ff to complete, then the `interrupted` halt with HEAD == candidate.

### N17b-L2 (LOW): the automatic undo expects only `--expect-fenced` fences, which can mismatch the restored bridge

**Where.** :2121 (`fenced=plan.request.expect_fenced`) → :2183-2186.

**Facts.**
- `--expect-fenced` must equal the stopped fences ∩ the **candidate's** `SENDABLE_IDENTITIES` (precheck :1452-1465).
- The restored PREV bridge prints its fences ∩ **its own** sendable set (paper_bridge.py:876-883). `fenced_by_printed_sendable` only intersects with the printed set; it cannot add a name.
- So suppose an identity is sendable in PREV, not sendable in the candidate, and stopped in the DB. PREV prints `CRITICAL fenced identities = X`, and the undo expects `none`. The result is `undo_dry_run` → exit 5, robot disabled.
- This happens only for a candidate that removes a fenced sendable identity. It fails closed.

**Fix.** Pass every stopped identity fence read at the precheck (`stopped_identity_fences`), not `expect_fenced`. The printed-sendable filter then yields exactly what the old bridge prints.

### N17b-L3 (LOW): the undo compares the old code's output with text built by the new code

**Where.** The undo's expectation uses the candidate's own `heartbeat_ok_line()` (:923-924: `presence_detail` text), `fenced_line` (:905-908), `SENDABLE_LINE_PREFIX` (:349) and `reviewed_line`/`schema_ok_line`. The dry run that is checked is PREV's.

**Facts.**
- P2 already compared `reviewed`/`schema`/`session`. P2.1 adds the heartbeat and fenced lines.
- Identical today (heartbeat.py and the bridge are untouched in the range).
- A future candidate that rewords `presence_detail` or the bridge's fenced line passes its own dry run. But every automatic or manual undo of it then fails `undo_dry_run`: exit 5, robot disabled.
- The dry-run variant test half-pins the heartbeat text (its `replace` must change the fixture), but nothing names this as a cross-version contract.

**Fix.** Either a test that pins these texts as literals, with a comment "changing one breaks rollback to every earlier head", or family-only matching in the undo (`heartbeat    Keychain item … present`, `… fenced identities = <set>`).

### N17b-L4 (LOW, owner experience): R5c's OPTION 1 has no time bound

**Where.** :2035-2060.

**Facts.**
- OPTION 1 tells the owner to enable a just-migrated candidate that has never started. The start expectation even allows `SESSION_START … after 07:55 ET`.
- O6 keeps deploys an hour clear of 07:55, and the manual window ended at 07:20.

### INFO

- **I-1. "git never moved" also prints after an undo already reset HEAD back.** An interrupt during the automatic undo *after* its reset gives HEAD == PREV, so the `next:` says "git never moved … enable". The action is right (PREV), but the wording is not, and the short `next:` skips the dry run. The stdout block (6.3) has it. Fold the wording into N17b-L1's fix.
- **I-2. Microsecond gaps.** A signal in two tiny windows propagates as a traceback with no halt line: after `wait_started` returns and before `signals_deferred()` (:1621-1623), or inside an `except` clause before `_halt_unexpected` enters `signals_deferred()`. Negligible.
- **I-3. Ignored signals are inherited.** Children started inside `signals_deferred()` inherit SIG_IGN for SIGINT/SIGHUP/SIGTERM: the `shadow agent disable` that `_undo_failed` → `_leave_disabled()` runs, up to ~75 s, cannot be Ctrl-C'd. This is by design ("a second signal is ignored") and harmless. launchd-started supervisors are not affected.
- **I-4. The rehearsal harness must inject the canonical paths.** It must set `DeployEnvironment.account_home` (to its fake home) and the DB at `<fake home>/.local/share/autotrader-v1/autotrader.db`, or every R1-R7 scenario now refuses `paths_not_canonical`.
- **I-5. The undo never checks the tree is clean (pre-existing).** Neither the ABORTED path nor `reset --keep` checks for a benign tree before restarting PREV. `--keep` keeps local edits by design. A partly applied failed merge would restart a mixed tree, which the dry run catches only for the bridge. N17b-L1's tree check closes this too.
