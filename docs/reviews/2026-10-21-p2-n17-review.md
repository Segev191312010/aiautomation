### MEDIUM-1: a stale confirmation stops the robot outside the window, and the undo can then leave it disabled mid-session

**Where.**
- deploy_apply.py:1135-1141 (`apply`): prechecks, then the plan, then `_confirmed`, then `_run`.
- :1329-1342 (`_confirmed`: a blocking `stdin.readline()` with no timeout).
- :1344-1356 (`_run`: PREV line, then `self.stop()`, with no window check in between).
- :1386-1390 (`_require_window`, called only before the fast-forward, :1358, and before the start, :1364).
- The undo's dry run (:1805-1821, session check :893-906) and start check (:1822-1829 → :1670-1693 → :1604-1610), both of which need `SESSION_WAIT date=<D>`.
- supervisor.py:803-805: `SESSION_WAIT` is emitted only `if self._clock() < opens`.

**Facts.**
1. `start_cutoff` is checked once in the prechecks (:1155-1157). The time between printing the plan and the typed sha is unbounded (`readline()`, :1339).
2. After the sha, `_run` writes the PREV line and runs `shadow agent disable` at once (:1347, :1354). There is no window check, no check that live HEAD is still `plan.prev`, and no recomputation of `plan.session_date`.
3. The window is re-checked only *after* the stop. A failure there raises `start_cutoff`, which on a code-only deploy goes to `_auto_undo` → `undo_to` (:1367-1370, :1757-1774).
4. `undo_to` stops, resets (a no-op here), runs the dry run for `plan.session_date`, enables, then `wait_started(... session_date=plan.session_date)` (:1805-1826). Both checks need a `SESSION_WAIT date=<D>`:
   - **The dry run.** `DryRunCheck.parse` always checks the session (:893-906). After 07:55 ET on the session day, `dry_run_report` simulates from *now* (supervisor.py:2049-2050), and the simulated supervisor writes `SESSION_START` with no `SESSION_WAIT` (supervisor.py:803-808).
     - Reviewer run (`tools/dryrun_late.py`, the real `dry_run_report`): `now` = Thu 08:05 ET gives `08:05:00  SESSION_START date=2026-10-22` → `dry_run_session`.
     - `now` = Thu 19:00 ET gives `SESSION_OVER date=2026-10-22` → `dry_run_session`.
     - So the undo stops with `undo_dry_run` before it re-enables (:1817-1821). It exits 5 with the robot **stopped and disabled**, and the printed 6.3 block's dry run fails the same way.
   - **The start check**, if it were reached, would also fail. A real mid-session start writes no `SESSION_WAIT`: the 2026-10-13 09:46 ET restart wrote `SUPERVISOR_START pid=86351 mode=daily`, `CHILD_START telegram`, `SESSION_START date=2026-10-13`, then started the screener, notifier, bridge and strategies at once (`supervisor.log.2026-10-17`:31-37, copy in `real/`). The waiter requires the line (:1604-1610), so the result would be `undo_post_start` and `_leave_disabled()`.
5. The tests never let time pass at the prompt: `FakeTTY` returns at once (test_deploy_apply.py:135-142). Both window tests advance the clock inside `disable` or the dry run (:1152-1180).
6. **Reviewer repro.** In a copy (`mut/c8/backend/tests/test_n17_repro.py`, never in the worktree), a `FakeTTY` whose `readline` advances the clock 12 h ran a plan printed at Sat 19:00 ET and typed at Sun 07:00 ET.
   - The PREV line was written, and `shadow agent disable` was called at `2026-10-25T07:00:00-04:00`, outside the window.
   - Then came `FAIL start_cutoff: before the fast-forward` and the automatic undo (exit 3 on a weekend; the fake supervisor always writes `SESSION_WAIT`).
   - Output: `~/autotrader-work/review-n17/repro-output.txt`.

**Failure scenario.**
1. The owner starts a deploy at 13:45 Israel (06:45 ET), as on 10-18 when the installs ran 08:55-10:50 Israel. The prechecks pass and the plan prints.
2. They are interrupted and type the sha at 15:05 Israel (08:05 ET, the session is live).
3. The supervisor is SIGTERMed. The screener and notifier stop; after 09:25 ET the bridge with open positions also stops.
4. `start_cutoff` fires before the ff, and the automatic undo starts. Its dry run for the session already under way has no `SESSION_WAIT`, so it fails `undo_dry_run` → exit 5. The robot stays **stopped and disabled** for the rest of the session:
   - no 15:45 flatten;
   - no telegram child, so no `/closeall` from the phone;
   - the printed manual block's dry run fails the same way.
5. A variant inside the window: the plan prints Thu 06:30 ET and the sha is typed Thu 19:00 ET.
   - The window is open again, so the ff happens. The dry run for the finished Thursday session fails (`SESSION_OVER`, `dry_run_session`).
   - The undo's dry run fails the same way, so the result is exit 5 with the robot disabled overnight.

**Fix (small: code plus one test).**
- Right after `_confirmed` returns True and before the PREV line, refuse with exit 78, nothing changed, when any of these holds:
  - `start_window_problem(self.now())` is set;
  - more than N minutes (for example 5) have passed since the plan was printed;
  - `self._live_head() != plan.prev`;
  - `next_session_date(self.now()) != plan.session_date`.
- Do the same in `deploy undo`: the session date is computed before its prompt (:1914-1921).
- Test: a `FakeTTY` whose `readline` advances `FakeClock` past 06:50 ET, and one that advances 6 minutes. Both expect 78, no deploys.log line, and `live.verbs == []`.
- Optional, as defence in depth: let `undo_to` recompute the session date and accept a mid-session restart (no `SESSION_WAIT`, `SESSION_START date=<D>` instead) in both its dry run and its start check, so a late undo never leaves the robot down for that reason alone. Weigh this against 6.3's "never mid-session".

### MEDIUM-2: after a migrate that printed no `backup` line, the printed restore points at a possibly stale backup (only with `--expect-migration`)

**Where.**
- deploy_apply.py:1360-1362: `state.migrated = True` is set before `migrate()`.
- :1494-1502: `MIGRATE_FAILED`/`MIGRATE_UNPARSED` with `backup=None`.
- :1720-1733 → :1882-1888: the restore's step 3 when there is no backup.
- The test enshrines the text: test_deploy_apply.py:2121-2136 asserts `"no backup line was read"` for `migrate_failed` and `migrate_unparsed`.

**Facts.**
- `db migrate` prints `backup    <path>` (db_admin.py:226) before it changes anything.
- Every refusal before that line leaves the database untouched:
  - `migrate_lock_busy` (:125-126);
  - a schema problem (:206-207);
  - the session window (:217-218);
  - a failed backup, "nothing was migrated" (:176-177).
- Even after the backup line, a failed apply is rolled back (:236-237).
- With `backup is None` the tool still prints steps 2 and 3 (:1878-1888):
  - move `autotrader.db`, `-wal` and `-shm` aside;
  - "find the newest `autotrader.*.v<N-1>-to-v<N>.db` in `backups/` and cp it".
- Backup names carry only a time and the version pair (db_admin.py:135-139), and nothing prunes them. An earlier attempt at the same migration leaves a same-pair file that is older than the live data.

**Failure scenario.**
1. A first attempt at migration 18 fails after its backup. The owner restores, the cause is fixed, and some sessions trade.
2. On the next attempt `db migrate` refuses before its backup line and prints none. For example, the backup cannot be written (disk full: `migrate_backup_failed`, "nothing was migrated"), or there is a schema problem. The tool halts (`migrate_failed`) and prints step 3.
3. The owner copies the *older* same-pair backup over a database that was never migrated. Every row since that backup is lost: fills, bracket ledger, **identity fence rows**, manual-order ledger.

**Scope.** It is unreachable in a code-only deploy (`_print_restore` runs only after `state.migrated`, :1368-1369, :1739-1742). The tool always runs from the candidate's worktree (:1175-1187), so the first migration deploy (P3-C, migration 18) uses the P3-C copy of this file. It must be fixed there or here, before any `--expect-migration` run.

**Fix.**
- With `backup is None`, print "the database was not changed (`db migrate` printed no backup line): skip steps 2-3". Add first `<python> <entry> db status --db-path <db>` with "Expect: `state     schema v<N-1>, this code needs v<N> …`". Then print only reset, dry run and enable.
- With a backup line but `migrated is None`, add the same `db status` check before step 2: v<N-1> means the migration rolled back, and steps 2-3 are not needed.
- Update test_deploy_apply.py:2133-2136.

### Q5 Stop waiter vs. reality

- **`stop()` (:1405-1421):**
  - `running` = a `_SUPERVISOR_PATTERN` process, or `supervisor.lock` held, read *before* the disable;
  - `since = floor_second(now)`;
  - then `shadow agent disable`. A non-zero exit is printed and the wait goes on (C11).
- **C11.** launchd.py runs each `launchctl` with `timeout=10` (launchd.py:45-52). `bootout` waits for the job, which may take up to ExitTimeOut 45 s (launchd.py:31-34). A timeout raises `LaunchdInstallError("unable to control the LaunchAgent")`, so the CLI exits non-zero while launchd keeps stopping the job. The waiter covers this:
  - `STOP_WAIT_TIMEOUT_S = 75` (> 45 s), counted after `disable()` returns;
  - pinned by `test_disable_timeout_error_still_waits`.
- **`_stop_state` (:1423-1447)** requires all of:
  - a non-empty `ps` table (an empty one never counts as stopped);
  - no supervisor;
  - no `_UNSUPERVISED_PATTERN` process other than itself (screener/shadow/notify/telegram `run`, `paper_bridge.py`, heartbeat without `--once`);
  - `lock_is_free(supervisor.lock) is True`;
  - when `running`, a `SUPERVISOR_STOP` line with `reason=SIGTERM` stamped `>= since`, from `supervisor.log` and its latest archive.
  - M11 (no lock probe), M17 (no `since`) and M55 (strays ignored) are each killed by a named `test_stop_wait_*` case. M18 (stop line never required) is killed by the happy-path test.
- **Lock probe:** `os.open(O_RDONLY|O_NOFOLLOW|O_CLOEXEC)`, `flock(LOCK_EX|LOCK_NB)`, released at once.
  - A missing file counts as free and is never created (`test_stop_wait_reads_an_o_rdonly_lock_probe_without_creating_the_file`).
  - The supervisor's lock is `<data>/supervisor.lock` (supervisor.py:315, :1849), the same path.
- **Real format.** The real 10-13..10-18 stops are `2026-10-18T07:46:01+00:00 SUPERVISOR_STOP reason=SIGTERM`: `fields[1]` is the kind, and `reason=SIGTERM` is a whole field.
- **"No supervisor was running":** `require_stop_line=False`, which prints a note (:1419-1420). The other conditions still apply.
- **Two limits:**
  - If launchd SIGKILLs at 45 s, no stop line is written, so the result is `stop_wait_timeout` → exit 4 with git untouched. This is conservative; see I-12 for the text.
  - Orphans of `manager run`/`research record|replay` are not in `_UNSUPERVISED_PATTERN`. Their windows end by 18:30 ET, before any deploy can start.
