**Evidence (my harness, full `run_notifier` loop, fake clock).**

### LOW-1: the very first page can already say "IBKR still refusing prices since 08:00 ET — restart IB Gateway now"

**Where.** notify_service.py:1179-1185 (the 08:30 backstop keeps the IBKR-side wording whenever `refused_at` or `ibkr_lost_at` is set, and backdates the streak to 08:00); `refused_at` is cleared only by a sweep (:1122); notify_service.py:1237-1241 (escalation by `checked_at - unreachable_since`, i.e. by the backdated start).

**Scenario (reproduced).** Six history timeouts 08:20:00-08:21:40 (one failure signal; no seventh), then a slow but healthy qualification, first sweep 08:36. First and only page, at 08:30:00: `⛔ IBKR still refusing prices since 08:00 ET — restart IB Gateway now`, then `✅ reconnected 08:36` at 08:38. "Still" on a first page, the wrong start time, it skips step 1 (log out elsewhere, the step that brought the orders back on 10-16), and it asks for a restart while data flows. Same if a refusal starts at 08:27 and the backstop fires before it opens. OPERATOR_PROMPT 4.9 says the 08:30 case is "log in", which is not what the code does here.

**Likelihood.** Rare: it needs a run of >= 6 timeouts each within 45 s and no sweep for 30 min. 10-13..10-15 had 0 history timeouts.

**Fix.** Escalate by the age of the IBKR-side evidence (first `refused_at` / first loss), not the backdated streak start; or never escalate on an outage's first page.
