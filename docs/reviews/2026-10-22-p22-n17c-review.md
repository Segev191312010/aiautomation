## Specific checks requested

**`signals_held` re-raise semantics** (:604-620; CPython 3.11.15).
- **Normal path.** On the main thread inside `signals_interrupt`, the previous handlers are `_raise_deploy_signal` for SIGHUP/SIGTERM and Python's `default_int_handler` for SIGINT.
  - `signal.raise_signal` runs the restored Python handler at once (it calls `PyErr_CheckSignals`). So `DeploySignal` or `KeyboardInterrupt` comes out of the `finally`, *after* git returned.
  - In `GitWriter._run` the `with signals_held()` sits inside a `try` that catches only `OSError`/`TimeoutExpired`, so the interrupt reaches `_run`'s `except KeyboardInterrupt` → `_halt_unexpected`, now with HEAD = candidate.
- **During an exception.** If `subprocess.run` raised (for example `TimeoutExpired` at 120 s) while a signal was held, the re-raised interrupt replaces it (the original is kept as `__context__`). The halt then sees the timeout's leftovers through `_tree_problem`: correct.
- **Off the main thread.** `signal.signal` raises `ValueError`, `_signal_handlers` swallows it before installing anything, `held` stays empty, and nothing is re-raised. Correct, as is the default handling.
- **Previous handler `SIG_IGN`.** The re-raise is ignored. This happens only when a git write runs inside `signals_deferred`, which never happens: the halts only read git.
- **Previous handler `SIG_DFL`.** Possible only for a `GitWriter` used outside `signals_interrupt` (tests). The process then ends as the signal asks, but after git finished. This is the intended "held, then delivered".
- **Two held signals.** Only the first is re-raised (its handler raises, which ends the loop). Harmless: the run is already halting.
- **Ctrl-C is deferred for up to 120 s** if git hangs (INFO; git runs with `GIT_TERMINAL_PROMPT=0` and stdin `/dev/null`, so it does not wait for input).

**`start_new_session=True` side effects.**
- git becomes a session leader with no controlling terminal: the terminal's SIGINT/SIGHUP never reach it.
- On the 120 s timeout, `subprocess.run` still SIGKILLs git's own pid, as before. Its leftovers (`index.lock`, a partial tree) are now caught by the tree checks: `undo_tree_dirty`, or 6.3 with the lock lines, never "git never moved".
- Credentials, editor and pager:
  - `merge --ff-only` and `reset --keep` are local and make no commit, so there is no credential helper or editor;
  - stdout/stderr are pipes, so there is no pager;
  - with no tty, any prompt would fail rather than hang (and `GIT_TERMINAL_PROMPT=0`).
- The argv is unchanged, so the AST test (`--hard` absent, only `merge --ff-only`/`reset --keep`) and the argv test are unaffected.
- The environment test still sees `git_environment(repo)`.

### N17c-L1 (LOW, regression in an edge case): a stale `index.lock` passes the prechecks; the deploy then stops the robot and the undo refuses to restart it

**Where.**
- `_tree_problem` is called only in `_halt_unexpected` (:2135), `undo_to` (:2258) and `_undo_prechecks` (:2574).
- The apply prechecks (`_prechecks`) and deploy_check's `check_tree_clean` never look for `index.lock` (deploy_check.py has no reference to it).
- `git status --porcelain` with `--no-optional-locks` succeeds with a stale lock present.

**Facts.** Reproduced in an archive copy (`~/autotrader-work/review-n17/mut22/x1/backend/tests/test_n17c_repro.py`, copy only), with `.git/index.lock` created before `world.apply()`:
1. every precheck passes;
2. `shadow agent disable` runs;
3. `FAIL merge_failed: git merge failed: remove the file manually to continue.`;
4. the ABORTED branch reaches the tree check and gives `FAIL undo_tree_dirty: …/.git/index.lock exists`;
5. the summary is `deploy apply: UNDO FAILED reason=undo_tree_dirty after merge_failed (exit 5; the robot is disabled)`.
- The live verbs are `['shadow agent disable', 'shadow agent disable']`, and the robot is not running.
- On 56e7be2 the same case ABORTED and restarted PREV (exit 3).

**Failure scenario.**
1. A previous run's git was killed at its 120 s timeout. That run ended exit 5 and printed the `rm <lock>` lines, but the owner did not run them. A Mac crash mid-git leaves the same lock.
2. The next `deploy apply` stops the robot and leaves it disabled again, without the ff having been possible from the start.
- This fails closed, and the owner is told the exact lines.

**Fix (one line plus a test).** In `_prechecks` (and `deploy check`, if wanted), refuse when `self._index_lock()` exists, before anything stops: exit 78, with the `pgrep -x git` and `rm` lines in the detail.

### N17c-L2 (LOW): a transient `index.lock` from a concurrent git reader at the undo's tree check gives exit 5

**Where.** `_tree_problem` looks once (:1555-1558).

**Facts.**
- A `git status` without `--no-optional-locks` takes `index.lock` for a few milliseconds to refresh the index: an IDE polling the live checkout, or an agent session whose working directory is `/Users/salomon/aiautomation`.
- If one lands at the undo's check, the undo refuses to restart PREV: exit 5, robot disabled. If one lands at the ff, the merge fails (pre-existing) and the ABORTED path then meets the same check.

**Fix.** In `_tree_problem`, when the lock exists, poll for up to about 5 s for it to disappear before reporting it. P2-5's runbook should also say: no IDE or agent git activity in the live checkout during a deploy.
